# 07 — The ML part: features, labels, training, deployment

*The pipeline is only "real-time ML" if the model is honest. This file is the list
of ways to be dishonest, and where each one is blocked in code.*

## 1. What we predict

`label = 1` means "this transaction was reported fraudulent" — in the demo, the
dispute/chargeback file the simulator maintains
(`generator/simulator.py:risk_probability` + `label_noise`). In a real acquirer it
is the same file, arriving **days to weeks late**. That delay is the whole
difficulty of fraud ML and it shapes three decisions here:

* labels live in their **own table** (`raw.fraud_labels`), joined at training time
  by `transaction_id` — never baked into the feature row. If a label sat in the
  feature table, a stale feature row would silently carry yesterday's verdict.
* training reads a **window that excludes the recent past** (nothing younger than
  the label delay), because a "mature" dataset is a *lie-free* dataset.
* the scorer never needs labels — it scores, and the label arrives later to
  `raw.fraud_labels` where the next training run finds it.

## 2. The features, and why they look like this

`jobs/common/features.py` is the single definition. Three families:

| family | examples | source |
|---|---|---|
| velocity / windowed | `txn_count_5min`, `amount_sum_1h`, `international_txn_count_1h` | event-time `RANGE` windows over the micro-batch + the `raw.card_minute_agg` / `card_day_agg` history tables |
| comparison / normalised | `amount_to_limit`, `amount_to_avg_1h`, `amount_zscore_24h`, `ratio_to_merchant_avg` | ratios against the card's own history and the merchant's typical ticket |
| context | `country_mismatch`, `merchant_risk_score`, `travel_notice`, `merchant_closed_hit`, `is_new_merchant_category` | joins to the CDC-maintained dimensions |

Why ratios and not raw amounts: a 4,000 transfer at a wire-transfer merchant is
Tuesday; a 4,000 transfer at a pharmacy is an incident. `amount_zscore_24h`
encodes "compared to *this card's* normal", which is what makes the model
transfer across customers. The same reasoning gives `merchant_risk_score` (from
the dimension table, so it updates without retraining) and `is_new_merchant_category`.

Two lists, and keeping them apart matters:

* `model_feature_names()` = the numeric features plus the three categorical
  *sources* (`channel`, `customer_segment`, `merchant_category`). This is the
  contract **the feature table and the Spark pipeline** agree on: the pipeline
  contains `StringIndexer` + `OneHotEncoder` + `VectorAssembler` for exactly those
  columns, so the vector is rebuilt from data, not from a stored order.
* `metadata["sklearn_feature_order"]` = the **expanded** list the sidecar model
  expects (`channel=online`, `merchant_category=crypto`, …). The REST API builds
  its numpy vector from this, because sklearn wants a flat matrix and has no
  encoder stages to carry.

Every name in the first list must exist in `FEATURES_TABLE_SCHEMA`;
`tests/unit/test_features_definitions.py` asserts it, because a missing column
becomes 0 in `ensure_feature_columns`, and a model trained on a zero-valued
feature is a bug you will never see in a log.

## 3. The four ways to cheat, and the guard for each

| cheat | what it looks like | guard in this repo |
|---|---|---|
| **label leakage** | AUC 0.999; `fraud_type`/`score` present in features | the wire payload has 12 fields, none of them labels; `tests/unit/test_generator_contract.py::test_wire_payload_never_leaks_ground_truth` |
| **random split** | great AUC offline, terrible live (the model saw the future) | time-based split only: `train_model.py` computes `cutoff = end - holdout_days`, `train = event_ts < cutoff`; no `random_split` exists |
| **stream/batch feature drift** | offline 0.93, online 0.71 | one definition (`rolling_features_sql`) used by both; `feature_store.py --verify` re-derives the same rows with the batch window function and prints `mean_abs_diff` |
| **accuracy on 2% positives** | "96% accurate!" | the job reports AUC, average precision, F1 at `--threshold`, precision/recall and the confusion counts — on stdout, and in `--metrics-out` for the Airflow guardrail. Accuracy is not in that list, on purpose |

The subtle one is #3. A "prior" window computed by a streaming join can include
the current row or not; whether your aggregate history is read *before* or
*after* the batch is written changes the number. `feature_store.py` therefore
reads history first, then writes, and the docstring at the top of the file says so
in words. If you refactor that job and `--verify` starts reporting a nonzero
`mean_abs_diff`, you broke ordering — not the verifier.

## 4. Training, step by step (`jobs/train_model.py`)

```
read features (dt in window) ── join labels ── split by time ──[undersample negatives]
  └─ StringIndexer(channel, customer_segment, merchant_category)
  └─ VectorAssembler(all model_feature_names)      ← saved INSIDE the pipeline
  └─ RandomForestClassifier(numTrees=120, maxDepth=12, classWeight=auto)
  └─ fit on train, transform test
  └─ metrics: auc, ap, f1, precision/recall@threshold, confusion, alerts/day
  └─ save: versioned dir {spark_model/, metadata.json, sklearn_model.joblib}
  └─ if auc >= --min-auc-to-publish and --publish true: move version.txt
```

Notes that matter:

* **`classWeight=auto`** instead of hand-tuned thresholds; `--undersample-negatives`
  exists for speed on big data (it biases probabilities, so the *threshold* must be
  recalibrated — that's why the threshold is stored in `metadata.json`).
* **Unseen categories:** every stage is `handleInvalid="keep"` (indexer, encoder,
  assembler), so a brand-new `merchant_category` gets an extra bucket instead of
  throwing and killing the micro-batch. `ensure_feature_columns` additionally
  coalesces NULL categoricals to `"unknown"`, so "no dimension row" and "new
  dimension row" behave the same way — one more reason the join miss in
  `docs/06-runbook.md` shows up as *quietly worse* scores, not an error.
* **`metadata.json`** holds feature list, order, types, categorical levels,
  thresholds, window, row counts, git sha, and the *label maturity* cutoff. Every
  consumer self-checks against it (see `model.load_pipeline_model` + the API's
  `ModelHolder.status()`).

## 5. Deploy = move a text file

```
s3a://lakehouse/models/fraud_rf/
   v20260909T090512Z/ {spark_model/, metadata.json, sklearn_model.joblib}
   v20260908T023011Z/ {...}
   version.txt                ← "v20260909T090512Z,<uri>"
```

* the streaming scorer calls `model.read_current_version()` each micro-batch and
  reloads if the version changed → **no restart, no deploy step**;
* `./artifacts/models/` gets a copy of `sklearn_model.joblib` + `version.txt` on a
  shared bind mount so the REST API serves the *same* model without a JVM;
* `make model-rollback` rewrites the pointer to the previous version;
* `POST /v1/model/refresh` forces the API to reload (the mtime watcher does it
  anyway within a second).

Guardrail: `--min-auc-to-publish` (the job's own default is 0.60; the Airflow DAG
passes 0.70, so a nightly run is held to the stricter number). The pointer is the *last*
thing written, after all files, and it's written by an atomic overwrite of a
one-row CSV. If training crashes mid-write, the previous model stays live — that
is the property you want from a deploy.

## 6. Monitoring a model you can't retrain daily

Fraud drifts in days, not years; what changes fast is *the population* (new
merchant, a campaign, a holiday). Three numbers, all in `serving.fraud_scores` /
`marts.data_quality_runs`:

| signal | why you care | query |
|---|---|---|
| score distribution shift | features changed, model didn't | `select width_bucket(final_score,0,1,10), count(*) from serving.fraud_scores where scored_at > now() - interval '2 days' group by 1` |
| alert volume per analyst | too high = noise, too low = broken | `select date_trunc('day', scored_at), count(*) filter (where is_alert) from serving.fraud_scores group by 1` |
| rule-vs-model disagreement | the model stopped flagging what a human can see | `select count(*) from serving.fraud_scores where rule_score > 0.6 and (model_score is null or model_score < 0.2)` |
| which model is live, and when | a deploy that didn't happen | `./jobs/submit/run_job.sh model_refresh --current` (and `--list` for the history) |

The alert-queue outcome (`confirmed` vs `cleared` in `serving.fraud_alerts`) is
your precision proxy: if analysts clear 90%, the operating point is wrong. Today
you move it by re-running training with a different `--threshold` (the value is
stored in `metadata.json` and served with the model). A natural first
contribution — and the one a real team builds first — is a small job that picks
the threshold hitting a target alert volume and writes it into the pointer's
metadata, instead of a human guessing every night.

## 7. MLflow (optional, off by default)

`MLFLOW_TRACKING_URI` set + `--mlflow on` logs params/metrics/artifact link per
run (`train_model.py:log_to_mlflow`). It is *not* the deployment mechanism:
`version.txt` is. That split is deliberate and worth keeping in a real team —
the registry is for humans comparing runs; the pointer is for a job that must
start at 3am with no network access to a tracking server.

## 8. Exercises that teach the most

1. Set `--algorithm lr` and compare AUC/alert volume. Linear models are hard to
   beat here, and seeing why (features are already ratios) is the point.
2. Remove `country_mismatch` from `NUMERIC_FEATURES`, retrain, and read the alert
   volume change. You just measured the value of one CDC-maintained join.
3. Set `GEN_FRAUD_RATE=0`, retrain, and watch the guardrail refuse to publish
   (`AUC ~0.5`, nothing shipped). This is the failure mode a notebook never shows you.
4. `make cdc-demo` mid-stream: close a merchant, then watch `merchant_closed_hit`
   fire on later transactions for the same card. Real-time features earning their keep.
